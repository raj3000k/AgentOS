# Security model

Model outputs and tool arguments are untrusted. AgentOS validates structure and scalar types and dispatches only to explicitly registered functions. It never evaluates model text as Python or shell code.

Registered functions and their annotations are trusted application code. SDK/CLI tools execute in-process; production workspace tools execute in supervised child processes with the same user's permissions. Register only functions you trust and expose only the minimum capability the task needs. Tool registration is not a sandbox or an approval system. A blocking or malicious function can still hang, allocate memory, access files, or use the network. Tool output size checks happen after invocation and serialization.

Step/call limits bound orchestration but are not wall-clock limits. Production workspace tasks additionally enforce a separate total worker deadline. HTTP timeouts apply to transport operations. The runtime does not roll back earlier tool side effects. Exceptions sent to the model omit arbitrary function exception messages; successful tool outputs and CLI JSON transcripts may still contain sensitive data.

The default Ollama endpoint is local. Selecting a remote endpoint or a remotely served model changes where inference happens. No proxy forwarding, HTTP redirects, telemetry, automatic disk logs, or cloud fallback are implemented.

Before exposing AgentOS to other users or untrusted tools, add process/container isolation, permission policies, hard deadlines, resource limits, and authentication at any network boundary. This MVP is intended for trusted local development.

A private vulnerability reporting channel must be configured before public release. Do not post credentials or sensitive transcripts in public reports.

## Local browser workspace and API credentials

The workspace listens exclusively on IPv4 loopback, validates the exact Host and browser Origin, and requires an unguessable per-server token on run requests. No CORS access is granted. Static assets are explicitly allowlisted, model output is rendered through DOM-built Markdown with raw HTML kept inert, and responses use no-store and a restrictive CSP. This is a trusted single-user local interface, not a remotely deployable authenticated service; other local processes can access it. Do not expose it through a public proxy.

User-selected API keys are passed in Authorization headers only to the selected API endpoint. Named providers have fixed endpoints; custom compatible endpoints are user configuration and must use HTTPS unless loopback. Proxy environment variables and redirects are disabled. Keys are not persisted, returned in results, or included in HTTP error bodies by AgentOS; Python/browser memory is not secure key storage. The page retains a key until cleared, provider changes, or reload. Cloud providers receive prompts and tool outputs and apply their own retention, access, and billing policies. There is no provider fallback or automatic discovery/import of tools.

Compatible APIs must support text Chat Completions and function tools when tools are enabled. Truncated/filtered responses and malformed tool batches fail before execution. Provider tool-call IDs and metadata are preserved for subsequent turns. The existing trusted in-process tool limitations remain unchanged. Production workspace workers can be terminated on Stop/deadline; in-process SDK runs still stop cooperatively. Neither mode provides an OS permission sandbox, resource quotas or rollback.

## Generated agent context

The prompt-to-context endpoint uses the same Host/Origin/token checks as task runs. It makes a single request to the user-selected provider with no registered tools. Generated output must match the bounded name/purpose/instructions/starter_prompts/assumptions schema; malformed output and tool calls are rejected without tool execution. The result is untrusted text rendered in editable controls. It is applied only by the user's Use this agent action and never imports code, registers tools, changes provider/key/model, or expands capabilities. With automatic selection, the model may recommend IDs only from the known available catalog, with reasons; these are reviewed/editable in the draft and are applied only by the user. Manual selections remain supported. The model cannot invent tools or select a file-access root. Instructions guide model behavior rather than enforcing security policy. Context/assumptions may be inaccurate; review them. Descriptions and generated drafts use the selected provider's normal data handling and billing. Profiles are stored only on explicit Save agent; run records only when Save this run to local history is enabled. Neither feature creates implicit conversation memory.

## Optional public web tools

Web research is opt-in; only the explicitly registered search/read/inspect functions are dispatched. The UI and CLI append an accurate capability description to run instructions, and brief generation receives the selected flags without executing tools. This remains trusted Python code running in-process, not a sandbox. Page content is untrusted evidence rather than instructions or executable code.

The HTTP reader makes GET requests only, with no authenticated sessions, cookies, model/API credentials, environment proxies, script evaluation, form submissions or browser control. It allows only HTTPS port 443 without URL credentials, resolves all candidate addresses and rejects non-global/private/loopback destinations, pins a validated public address for the TLS connection while preserving hostname/certificate verification, and revalidates redirects. Each run has 20 HTTP requests including redirects, a 512 KB per-response cap, up to three followed redirects and 12-second network-operation timeouts. These do not provide a hard overall deadline or process/resource isolation. Rendered/script-only pages are unsupported. Providers can block automated reads; no bypass is attempted.

Queries and URLs go to LinkedIn/Bing/public destination sites; page evidence goes to the selected inference provider. The model should never put secrets into query strings. Application URLs are extracted evidence, not a guarantee of role identity or availability. Hidden links, Easy Apply, closed roles and unverified external URLs are reported separately. Source/application anchors are rendered as validated HTTPS links with noopener/noreferrer; all page/model text uses textContent. Page results are trimmed to fit tool-output budgets. Network request logs are not persisted by AgentOS.

## Budget finalization

Research runs reserve the last configured model request with no tool schemas and disallow tool execution during finalization even if a model requests it. A tool batch exceeding the remaining budget is skipped entirely; its assistant tool calls are not left unanswered in the summary transcript. No additional requests exceed the configured total model budget. Summary failure, invalid/empty content, or continued tool requests produce marked partial output using only collected tool results. This preserves evidence rather than granting execution permissions or retrying side effects. SDK callers retain strict RunLimitError behavior unless they explicitly enable finalize_on_limit or plan_task (planning reserves the final request for a tools-disabled summary). Completed summary text is still model-generated and may need review; budget_summary/partial metadata indicates potentially incomplete work.

## Expanded capabilities and browser rendering

The catalog is a fixed ID allowlist. Automatic description-to-agent selection returns validated IDs and short reasons, not imports, executable code, URLs to install, or a permission-policy program. Applying the draft is the user action that enables reviewed choices. File-reading recommendations cannot grant access until the user configures a specific folder. Local file tools list/read only supported text types, block relative escapes/hidden paths/symlinks/credential-like names, cap read/output sizes, and never write or execute. Filters are not secret detection or OS isolation; user-selected file contents may go to the selected cloud model.

Data tools operate on supplied text using csv/json/regex/statistics, not eval or generated expressions. Writing/summarization and code review are instruction skills, clearly distinguished from registered action tools. Employer job tools GET published Greenhouse/Lever APIs only; no applications or personal details are submitted. URLs are still subject to public-network validation.

The optional Playwright/Chromium module is explicitly trusted, static application code, not dynamically loaded model code. Chromium executes third-party page JavaScript in a fresh context. No user browser profile/session is attached. Every routable HTTP resource is supplied through the DNS-pinned HTTPS reader; methods other than GET, private destinations, websockets, service workers and unnecessary media are blocked. Cookies and auth headers are never forwarded; response Set-Cookie is removed. A fixed init script disables WebRTC peer connections; no model-supplied JavaScript/evaluate input exists. There are no click, fill, login, screenshot-upload, form-submit or download tools. This is a bounded renderer, not an unrestricted browser agent or guaranteed anti-bot bypass. Browser budgets/operation timeouts do not provide a hard run deadline or complete system-level resource isolation.

## Answer formatting and downloads

The formatter uses createElement/createTextNode/textContent, never innerHTML, eval or model-controlled DOM/event code. Only a known Markdown subset produces predefined elements. Raw HTML and image markup never create active HTML/images; answer links accept HTTP(S) only with no credentials and open with noopener/noreferrer. Clicking a model-provided link is not evidence that it is verified; tool-source cards remain separately labeled. No remote assets, scripts or fonts are fetched for formatting.

Code blocks are display-only with user-initiated copy. Checklist changes, table filters and sorting affect the current display, not the agent or original answer. Markdown/CSV downloads are user-initiated local Blob artifacts and the temporary object URL is revoked. Markdown preserves model text exactly; CSV includes currently visible/sorted rows, quotes cells and prefixes cells with leading formula markers to reduce spreadsheet formula execution risk. Preview/table limits bound rendering; complete raw output remains available. Saved results may be explicitly archived in the local workspace database; formatter interactions themselves are not persisted.

## Local saved agents and run history

The production web server uses `.agentos/workspace.sqlite3` under the caller's working directory. The directory/database are Git-ignored, with newly created directory mode 0700 and database mode 0600 on POSIX; existing parent directory permissions are not changed. SQLite connections are request-local, use parameterized record values and allowlisted table names, and enforce schema version 1. Unknown newer schema versions are rejected. This is local storage, not an encrypted vault or a multi-user authorization layer; other processes with the user's filesystem permissions can read it.

Saved agent data is a validated field allowlist. API keys and file-access directories are not saved in profiles or run settings. Loading any saved profile clears the current key/folder and requires a fresh configured folder before file reads; unavailable optional capabilities are omitted from the loaded session. The stored model/provider is shown explicitly before the user submits a new task. Stored profiles are data, never executable imports/tools.

History is off by default and records runs only after the user enables its checkbox. It stores prompts, original transcript/tool outputs, formatted-answer source text and partial/error metadata, which may themselves contain sensitive user-provided content. Excluding the request API-key field is not content secret detection. Credentials intentionally pasted into prompts or returned by trusted tools can appear in an opted-in record. There is no automatic background capture or implicit cross-conversation memory; retained turns enter context only through the active conversation or explicit continuation.

Library reads require the workspace request token and exact Host; saves/deletes use the existing Host/Origin/token checks. UI deletion requires confirmation. SQLite secure_delete is enabled, but filesystem backups or other copies are outside the application's deletion guarantee. No automatic database replacement, cloud synchronization or remote storage is performed. A history-write failure leaves the completed answer usable and reports that saving failed.

## Live execution events and cooperative stop

Streaming run and stop requests require the same Host/Origin/token validation as other mutations. Run IDs are client-generated canonical UUIDs and live only in a per-server locked registry, capped at four active streaming runs and cleared on all exit paths. The cap includes legacy JSON requests in isolated mode; it does not limit context-generation requests or isolate CPU/memory. No new worker pool, persistent event archive or model-controlled callback is introduced.

SDK lifecycle callbacks and stop predicates are explicitly supplied trusted application functions. Checks before/after model requests and before each registered tool prevent later operations after an observed stop. In-process SDK tool/model calls cannot be killed; production workspace workers are terminated on Stop/deadline. Existing per-operation timeouts still apply. Cancellation retains tool evidence in a `cancelled` result, optionally saved through the same opt-in history mechanism. Interrupted transcripts may have unanswered tool calls for the unexecuted remainder of a batch; these transcripts are for inspection, not resumption.

Lifecycle events omit prompts, arguments, returned evidence and model reasoning. Explicit plan events contain bounded generated titles, criteria, notes and reference IDs; these may echo sensitive task data and are not a secret-redaction boundary. The terminal result still contains the normal answer/transcript and must be treated as sensitive. A failed stream write sets the stop flag, but tab closure need not be detected while an operation is blocked. Disconnects do not guarantee an immediately stopped run. No automatic retries are performed.

## Explicit conversation context

Retained context is a bounded field allowlist: user prompt, assistant answer, completed tool evidence (name/content), and completion status. System/developer roles, executable calls, extra credential fields and arbitrary provider metadata cannot be supplied through this format. Current instructions and tool registration are rebuilt for every request. Prior evidence is labeled untrusted/historical and may be stale or contain prompt injection; labeling is not a sandbox or a guarantee of model correctness. No old tool calls are executed, including pending calls from cancelled batches.

The browser holds its active conversation in memory. Follow-up submissions send the retained turns to the currently displayed inference provider. Changing instructions, capability selections or model connection clears active context before the next task. Explicit Continue conversation loads an opted-in snapshot, resets keys/folders through the existing profile loader, and runs no inference until the user submits. Entering a new file folder grants only current registered read tools; history does not restore filesystem permissions. Existing evidence can contain previously read data regardless of current capabilities.

Saving a follow-up explicitly saves all of its retained turns, including earlier turns that were never individually saved. A snapshot is independent of other archive records; deleting an earlier record does not erase copies in later snapshots. Existing SQLite permissions/secret-content limitations apply. The database schema stays at v1; new optional result JSON fields preserve compatibility with old view-only archives. Failed runs preserve the live browser context, but their archived error record may not contain prior conversation turns.

Validation caps retained context at 20 turns/256,000 serialized bytes, with 64 evidence records per turn and 16,000 characters per evidence result. Run request bodies allow 512 KiB to carry that context; other POST endpoints retain the 64 KiB cap. These bounds do not estimate model tokens or guarantee every model can accept the context. Full context is rejected explicitly rather than silently truncated. A newly completed answer too large to retain remains usable but requires a fresh conversation for further work. There is no global memory, automatic server-side session state, cross-user isolation or history-based tool authorization.

## Supervised workspace workers

`serve` uses `make_server(..., isolate_runs=True)`. Default SDK/test servers keep the explicit in-process path; `/api/workspace` exposes the distinction and unsupported hard-deadline requests are rejected. Each isolated task launches the fixed `python -m agentos.worker` entry point using the current interpreter and no shell. No model-controlled module, command or executable path is accepted. The worker rebuilds only the static trusted capability catalog; registered execution occurs there. Agent brief generation remains in the server with its provider timeout.

Validated request settings, API key and conversation pass through a private stdin pipe, not argv/temp files. Worker stdout is reserved for bounded JSON protocol messages; normal library/tool prints are redirected to discarded stderr. Environment inheritance and same-user process access remain outside credential isolation. Checkpoints include current transcript and attempted model/completed tool counts. They are sensitive internal state; lifecycle events still omit content, while explicit plan events expose bounded user-facing plan data. The parent saves only the normal opted-in result fields, excluding request keys/folders.

An independent watchdog terminates the worker at the configured 5–1800 second deadline (300 default) or observed Stop, including while an observer is blocked. Deadline timing starts around worker launch, after server configuration validation; response delivery and process-reaping overhead are separate. The parent reaps workers and closes pipes on success, errors, deadline, Stop and callback failures. POSIX process-group termination reaches descendants still in the worker group; Windows direct-worker termination does not guarantee descendant cleanup. A process that deliberately escapes its group is outside this mechanism. Server close signals active workers to stop. Four isolated requests share a per-server cap, whether streaming or legacy JSON.

This is not a sandbox: filesystem/network permissions, inherited environment, CPU/memory access and trusted tool privileges remain those of the user. No untrusted custom tools become safe. Termination cannot roll back side effects or guarantee remote/Ollama inference cancellation/billing cessation. Only completed evidence received by the parent is retained; interrupted operations may have unreported effects. A `timed_out` result remains explicit, can be archived, and its completed evidence can be continued as historical data without replaying unfinished calls.

## Visible plans and completion assessments

Planning is explicitly enabled through a boolean run setting (new UI agents default on; SDK/HTTP default off). A single tools-disabled request creates a strict 1–6 step JSON plan with bounded title/criterion fields. Invalid plans fall back to one user-task checkpoint. Proposed tool calls/code/extra fields never execute during planning. The planning request counts toward max_steps, progress updates count toward max_tool_calls, and existing deadlines/Stop/finalization remain active. No extra hidden evaluator request is made.

`update_task_plan` is a reserved, statically trusted control tool bound to this run’s plan. It changes progress data only. IDs/statuses/notes/reference strings are validated; completed or blocked states require a note. References must name existing successful current-run task-tool executions, not control-tool self-citations, invented IDs or failed invocations. This verifies reference existence/return status only: it does not validate source truth, relevance or satisfaction of the criterion. Tool result content may still report an unavailable source. Models can be mistaken or deceptive about progress; all completion claims remain explicitly labeled model assessments. No answer automatically completes untouched steps.

Plans never authorize actions or change the selected registry/permissions; only the existing trusted capability functions execute. The control-tool name is reserved when planning is enabled to prevent accidental registry shadowing. State is per run, with no model-selected import, eval, shell or executable planning language. Successful task results carry bounded evidence-reference metadata; 100 characters of tool output allowance are reserved for it. Plan-control messages remain in the inspection transcript but are excluded from retained conversation evidence and partial evidence summaries.

Plan events include limited generated descriptions/notes that may echo prompt or result data. They use textContent/predefined DOM elements, not executable HTML. Current plan/checks are included in private worker checkpoints and opted-in result archives; interrupted work is not silently completed. Completion checks mean reported-status/reference consistency, never independent verification or proof that an external action occurred.

## Job-quality evidence and destination checking

`build_capabilities` attaches a bounded per-run collector to statically known research functions and registers `review_job_results` / `verify_job_application` only when a research capability is selected. Trusted wrappers retain each Tool's original scalar signature/schema/validation. The model cannot submit job records or claim its own verification metadata through these tools. The SDK caller remains trusted and can replace application tools/data; this is not protection against a malicious embedding application.

Collected records come from actual tool returns and include original source URLs/timestamps and bounded descriptions/parsed experience. The collector holds at most 100 observations/256,000 serialized characters, reports truncation and resets on each Agent.run through an explicit `Tool.on_run_start` application callback. This optional callback is never in a tool schema and cannot be supplied or invoked as code by the model. Registered lifecycle functions are trusted synchronous code with caller permissions; exceptions propagate. Reusing shared mutable tool instances concurrently is not an isolation guarantee; production workers construct fresh registries.

Review is deterministic, using bounded English patterns and source/ATS identities. A confirmed category means explicit criteria and exact known feed destination identity agree, not that the employer is authentic, all eligibility requirements are met, or a form accepts submissions. Source content can be wrong or malicious. Descriptions are parsed before display truncation; required minimum years, preferences/ambiguity, closure text and ISO deadlines remain heuristic signals. Conflicting/unknown evidence is not silently confirmed. No independent job-truth oracle is implemented.

Verification accepts only an already captured source's observed application destination. Known Greenhouse/Lever URLs are read through their existing exact-job API parser; other specific destinations receive a public-page reachability check only. Unknown sources and generic/Easy-Apply destinations do not trigger guessed reads. The verifier shares a dedicated eight-GET budget per run with its API/page reader, using the existing HTTPS-only, DNS-pinned/private-IP/redirect checks, response caps and no cookies/auth/proxies/submissions policy. Model/provider API keys are never passed to public sites. Missing/blocked APIs downgrade confidence rather than proving closure.

Deduplication strips known tracking parameters for comparison only, preserving actual links and semantic job-ID query values. Stable job IDs are scoped to platform/employer. Titles alone are not identity. A closure signal suppresses application shortcuts; generic career pages are not exact application URLs. Review output/links use predefined DOM/textContent with safe-link validation, so page strings do not create active HTML. Report filters are local display interactions. Opted-in run history stores the tool messages containing the review under existing sensitive-content rules. No automatic network/model calls happen on display/reopen, and historical conversation evidence is not imported into the live collector.


## Optional authenticated LinkedIn tab bridge

The user explicitly installs the bundled Chrome extension, invokes its toolbar on a chosen LinkedIn tab, and clicks Connect this LinkedIn tab in the panel. The fixed controller first validates the active LinkedIn origin and activeTab script permission, connects to the local workspace, obtains a fresh token-protected random bridge credential and keeps it internal. No code is displayed or copied. Merely opening the extension does not pair or capture the page. Extension permissions are activeTab, scripting, storage, alarms, sidePanel and the fixed default loopback workspace host; no cookies, debugger, broad LinkedIn host access, browsing history or all-tabs permission is requested. The extension can read/navigate only its selected tab while Chrome's activeTab grant remains valid. Its connection UI discloses the tab navigation and job-data access before pairing. Loading an unpacked extension is a manual user step, not silently performed by AgentOS.

The separate bridge credential cannot authorize workspace CRUD. Commands permit only canonical www.linkedin.com job search/detail URLs; server and extension both validate navigation. No request accepts a script, selector, arbitrary action, file path or model-provided function. A fixed, packaged DOM extractor reads scoped job content. Replies have a 180 KB request cap, rendered descriptions and link lists are bounded, and tool envelopes retain the standard limits. Treat all returned text/links as untrusted source data. Anyone who obtains the bridge credential can issue job-page reads, inject bridge results, or disconnect it: do not share pairing codes. The trusted local extension is part of the execution boundary, not a source-attestation system.

Only one bridge command can execute at a time; concurrent runs get session_busy instead of racing the shared tab. Commands expire after 30 seconds and are delivered at most once. Disconnect/rotation invalidates pending work and old credentials, though a navigation already delivered to Chrome can finish independently of worker termination. Status uses a recent heartbeat, not proof of an authenticated login. If tab access is revoked/closed, or LinkedIn presents login/verification/challenges, reconnect or let the user complete the checkpoint; do not bypass it.

Authentication stays in Chrome. The extension retains only tab ID/bridge code in chrome.storage.session. Python never reads browser cookies, credential databases, profile directories or debugger endpoints. Selected provider inference receives job fields (and any sensitive information present within those fields); opt-in history can retain that evidence. Pairing secrets stay out of model context, archives and profiles. The browser's normal page loads can perform site scripts, telemetry and non-GET resource requests: authenticated tab browsing does not inherit BrowserReader's DNS-pinned GET-only SSRF guarantees or constitute a browser/network sandbox. No tools click Apply, fill fields, submit applications, send messages or navigate to account/profile pages. External application URLs are extracted and verified through existing public-page tools where possible, not automatically opened through the authenticated tab.


## Browser Companion side panel

The broader companion reads only an HTTPS tab explicitly added after the user invokes the extension toolbar on that tab (Chrome activeTab). There is no tabs/history/cookies/debugger permission or all-sites host grant. A fixed trusted extractor takes at most 3,500 characters of visible main/article/body text, excluding form/editable content, scripts and common navigation; up to four snapshots may be shared per task. Private statements can still occur in visible text, so the panel offers previews and states that Send shares the snapshots with the selected model. Generic source tabs are not navigated by the agent. Sources are untrusted quoted data; model text never becomes a browser function, selector, executable script or arbitrary action.

Explicit Connect reads the local workspace's request token into extension background memory using the fixed loopback host permission. This makes the installed extension trusted with workspace authorization: it must be reviewed like other trusted local tooling, not treated as an untrusted third-party client. The shipped controller calls stream/Stop and the explicit LinkedIn pairing endpoint. The server permits valid chrome-extension origins only for those three POST endpoints and still requires the unguessable workspace token and exact loopback Host. Other origins and extension-origin profile/history CRUD or workspace-token disconnect writes remain rejected. Bridge-authenticated disconnect remains scoped to that connection. Workspace tokens cannot be protected from already-privileged malicious extensions with loopback access; there is no claim of independent identity attestation or sandboxing.

Provider keys are held by the panel/active request and excluded from chrome.storage.session, saved settings, source records, model instructions and conversation state. Sources/non-secret settings/conversation are in session storage rather than workspace history; Clear sources & chat clears them, whereas New chat clears only retained conversation. Old snapshots can remain in prior conversation until that reset. Server/browser restart requires reconnecting; the browser controls extension worker lifetime and may interrupt the live stream. Interrupted restoration is labeled and the server's normal deadline/worker cleanup remains the final lifetime bound. Stop may be requested before the started event and is delivered when the run ID becomes active. Form filling, arbitrary clicking and consequential submissions remain outside this milestone.


LinkedIn compatibility reads on the modern generic layout remain field-scoped: title/company from visible/document title, location from the header, and description only inside a bounded About the job section with a known end marker. The body fallback is not returned wholesale, and absent boundaries return no description. Visible Apply anchors may include LinkedIn safety/go redirects; only their observed URL parameter is unwrapped and validated as a public HTTPS target. Hidden/off-screen CAPTCHA widgets are not treated as active challenges, but substantial visible challenge frames and login/checkpoint URLs still stop the read. These layout heuristics are not a guarantee of complete content or site identity.


At a connected posting-read deadline, the extension may return its last scoped job fields with an incomplete-description label. This does not broaden page access or fill missing requirements. Navigation-away/login/challenge failures do not become successful partial reads. Observed application links remain unverified until checked.


## Hosted adapter

The Node/Netlify adapter has a separate Google identity and per-user storage boundary; it never exposes the Python loopback server. Read [HOSTED_RELEASE.md](HOSTED_RELEASE.md) for JWT/nonce/session/CSRF checks, immutable usage claims, retention, registered source hosts, cloud limitations and outstanding production checks. Browser tabs, cookies and local credentials are not forwarded to hosted runs. Shared-key public access remains a small capped demo, not hardened multi-tenant production hosting.
