## Goals and scope

Build a lightweight, understandable, local-first Python AI agent framework using Ollama, initially `qwen3:8b`. Provide an SDK, explicit custom tool registration/execution, a CLI, and deterministic offline tests. Prepare for eventual open sourcing without premature infrastructure. The first milestone is a synchronous single-agent runtime; implicit conversation memory, multi-agent coordination, token streaming and OS permission/resource sandboxing remain future milestones. Production workspace tasks now execute in supervised workers with total deadlines; SDK/CLI custom tool execution remains trusted and in-process. Lifecycle activity streaming and immediate worker stopping are implemented in the production web workspace; SDK/test in-process mode retains cooperative stopping. Explicit local saved-agent profiles and opt-in run archives now use SQLite. Follow-up conversations retain bounded prior prompts/answers/tool evidence in page memory and optionally in saved snapshots. Optional task planning adds bounded visible steps, model-reported progress and completion/reference consistency checks. Job research now includes deterministic matching/deduplication and exact observed-destination review over captured tool evidence. A local web UI, optional user-key API providers, and a fixed ten-entry capability catalog (including opt-in public research, employer feeds, optional browser rendering and scoped text/data tools) are now implemented.

## Architecture

`Local browser / CLI / Python caller -> Agent.run -> ChatClient -> Ollama /api/chat or compatible API /chat/completions -> assistant tool calls -> registered Tool.invoke -> tool result messages -> next model turn -> RunResult`.

Each run starts with current system instructions, explicitly supplied validated prior turns (if any), and the current user message. The runtime preserves assistant messages, appends named tool results, and repeats until a nonempty final answer. All tools in a response execute sequentially. The full batch's wire structure and remaining budget are checked before execution. Tool argument/execution errors become JSON error results so the model can recover. Provider failures and budget exhaustion raise public exceptions. There is no retry of HTTP requests or failed tool functions, avoiding accidental duplicate side effects.

## Design decisions and trust boundary

- Python 3.11+ core uses only the standard library at runtime. Optional browser extra installs Playwright/Chromium; base runtime still has no mandatory dependencies. Setuptools is required for packaging. A small HTTP adapter and injectable protocol keep tests independent of Ollama.
- Use Ollama's native `/api/chat` tool schema and `tool_name` responses, `stream: false`, `think: false`. Preserve assistant fields in the transcript. Reference: https://docs.ollama.com/capabilities/tool-calling and https://docs.ollama.com/api/chat (checked 2026-10-13).
- No `eval`, generated code execution, shell tool, filesystem tool, auto-discovery, or model-selected imports. Calculator dispatches only four known arithmetic operations.
- `@tool` accepts synchronous functions with explicit scalar `str`, `int`, `float`, `bool` parameter annotations, optional typed defaults, and JSON-serializable results. Reject variadic, positional-only, async, and generator functions. No coercion; booleans do not count as integers. Complex parameter schemas are deferred.
- Registered Python functions are trusted code with caller permissions. SDK/CLI custom tools run in-process without hard interruption; production workspace tools execute in separately supervised workers that can be terminated. Neither path is an OS permission sandbox or output-allocation/resource quota. Add a permission/resource sandbox before supporting untrusted tools.
- SDK/CLI defaults remain 8 model steps and 16 tool calls; workspace defaults are 16/24. SDK `finalize_on_limit=False` preserves raising RunLimitError on exhausted budgets. UI/CLI runs with action tools enable finalization: reserve the final allowed model request, provide no tool schemas, and request a summary based on collected evidence. Tool-budget overflow skips the whole batch and uses a remaining request to summarize. Ignored stop instructions, empty/invalid summaries, or a ProviderError during finalization yield a deterministic partial result with collected evidence. No extra request beyond max_steps and no tools execute during finalization. RunResult includes finish_reason (completed/budget_summary/partial/cancelled/timed_out), optional limit_reason and explicit conversation/context_error data. Tool count includes failed calls. Normal result envelopes are limited to 16,000 characters; oversized/non-JSON results become errors. HTTP reads cap responses at 2 MB; timeout defaults to 120 seconds per request, not a whole-run deadline.
- Default host is loopback. Explicit remote hosts are supported and send prompts/results there. Ignore environment proxies and reject redirects; no telemetry or hidden hosted API fallback. Model names are caller configuration, not validated as local-only model tags.
- API adapter uses text Chat Completions with optional function tools; normalize JSON-string arguments into validated objects and serialize them on subsequent turns. Preserve call IDs and provider metadata (including Gemini signatures), attach tool_call_id to results, reject malformed/truncated/filtered responses, and omit raw provider error bodies. No automatic request retries. Named API endpoints are fixed; custom HTTPS endpoints are explicitly user-selected. HTTP permitted only for loopback compatible endpoints. Native non-compatible APIs are out of scope.
- Browser server binds only to 127.0.0.1, validates Host/Origin and an unguessable request token, caps run request bodies at 512 KiB and other POST bodies at 64 KiB, validates settings, uses an asset allowlist/CSP/no-store, and builds response elements through a predefined Markdown subset using DOM nodes/textContent, with raw HTML/images inert. Local UI Ollama endpoints must use loopback. API keys remain only in page/request memory and clear on provider change/reload; AgentOS never stores request credentials; transcripts are stored only with explicit per-run history opt-in. Same-machine processes are trusted; this is not a public authenticated service. Production tasks use isolated worker lifetimes and total deadlines; SDK calls still stop cooperatively. Neither mode is an OS permission/resource sandbox.
- Prompt-to-context uses exactly one provider request with no tool schemas; rejects returned tool calls without execution. Validate a JSON object containing bounded name/purpose/instructions, starter prompts and assumptions; permit a surrounding JSON code fence only. Returned text is an editable draft, never executable code or a permission policy. It cannot register tools, grant access or change provider/model. Manual selected IDs or opt-in automatic recommendations are separate validated data from a fixed catalog. Automatic mode adds capabilities/capability_reasons to the brief schema. A fixed research recipe adds available employer feeds for web job tasks and an available renderer for LinkedIn/JS/browser tasks, with explicit fallback reasons; manual selection is unchanged. Available selections are editable in the draft and applied by the user; folder access requires separate user configuration. Applying is a user action that replaces the current name/instructions; displayed purpose remains descriptive. Assumptions must be reviewed; generated briefs are not guaranteed correct. Provider or validation failure leaves the previous draft/active context intact.
- Optional public web research is explicitly registered only when enabled. `search_linkedin_jobs` parses public search candidates; `inspect_linkedin_job` returns posting evidence and application status (external link, LinkedIn Easy Apply, login-required, unexposed, closed or unavailable). `search_web` uses best-effort Bing RSS for matching employer pages; `read_web_page` returns bounded page text/links. No invented destinations or automated open-role verification. These HTTP-only tools have no browser rendering, JavaScript, login, cookies, CAPTCHA bypass, downloads to disk or applications. Optional browser rendering is a separate capability.
- Web fetcher uses stdlib HTTPS GET on public port 443 only; reject credentials/private/non-global addresses and pin validated DNS addresses while retaining TLS hostname checks. No environment proxy forwarding. Revalidate each redirect; cap to 3 followed redirects, 20 HTTP requests per toolset/run, 512 KB per response and 12 seconds per network operation. Trim result JSON below 14,000 characters to fit normal tool envelopes. DNS and network timeouts are not hard run deadlines. Website structure/search relevance/blocking can change. Web evidence is untrusted data; model/API secrets are never provided to these tools. Queried public sites and the selected inference provider receive the respective queries/page text.
- SDK runs have fresh in-memory state unless validated history is explicitly passed; the browser retains only its active conversation. JSON CLI output contains the full transcript; callers are responsible for protecting it. No implicit conversation memory or default task logging. Explicit profile saves and opt-in run history are stored in local SQLite.
- Distribution working name is `agentos-local`, import is `agentos`; registry availability/name conflicts and license selection must be checked before publishing. No package or repository has been published.
